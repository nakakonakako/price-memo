# 仕様: レシート管理（A）と厳密単価比較（B）の分離

最終更新: 2026-08-28

> 本ファイルは隣リポジトリ `receipt-manager/docs/spec-split-receipt-and-unit-price.md` を前提にした写し＋B 視点の注記。  
> A 側のメモ / `is_comparable` / `memo_rows` は **A から削除済み**（2026-08-25）。厳密単価・推移比較は **本リポジトリ（B）の責務**。

## 1. 一文まとめ

レシート管理アプリ（A）は「どこで何をいくら使ったか」の汎用的な記録・検索・管理に特化する。  
厳密な単価比較（B = 本リポジトリ）は独立し、手動フォルダで比較対象を管理し、必要時のみ A のレシート DB を一方向参照する。  
B は支出管理ではなく **単価の統計アプリ** であり、店頭では OCR より **買い物メモ（統計＋試算）** を主とする。詳細: [spec-shopping-memo.md](./spec-shopping-memo.md)。

## 2. 背景と決定理由

### 2.1 問題

| 論点 | 内容 |
|------|------|
| 情報の非対称性 | レシートだけでは g / 個数が取れない。生鮮は事後補正がほぼ不可能 |
| 目的の混同 | 「いくら使ったか」と「100g単価でどこが安いか」は必要な粒度が違う |
| 両立コスト | ラベル写真・紐付け・選択 UI を記録フローに足すと本旨から離れる |
| 中途半端な比較 | メモの総額比較は「動いている感覚」があり、厳密比較の価値を曖昧にする |
| 仮定値 | デフォルト重量などは比較として信用できないため採用しない |

### 2.2 方針決定

- 厳密さを優先する。ざっくり比較を A に残さない。
- A と B を共存させすぎると UI・データモデルが破綻するため、関心を分離する。
- インストアコード / JAN による生鮮重量の汎用自動取得は当てにしない。
- 店頭の主手段は値札 OCR ではなく、事前統計を見る **買い物メモ＋短い試算** とする。

## 3. 責務分離

### 3.1 機能 A: レシート管理（`receipt-manager`）

**目的**: 汎用的な支出・購入履歴の記録、検索、管理。

**やらないこと（B へ移管）**

- 重量・個数・100g単価の入力・保持を本流にする
- 厳密比較対象の取捨選択 UI
- 値段推移グラフ / 店舗間の厳密比較
- 店頭での単価判断 UI（旧「店頭照会」構想を含む）

### 3.2 機能 B: 厳密定義・単価比較（本リポジトリ）

**目的**: ユーザーが意図した商品だけを、g / 個数 / 全体重量などで厳密に記録・比較する（統計）。

**やるべきこと**

- 手動フォルダ（カテゴリ）による比較対象の整理
- 厳密レコードの記録（購入日・店・値段・数量。買わなかった観察も含めてよい）
- 値段推移・店舗比較
- **買い物メモ**（統計一覧＋行内試算＋任意保存）— [spec-shopping-memo.md](./spec-shopping-memo.md)
- 必要時に A のレシート明細を検索して下書き／参照紐付け（任意）

**やらないこと**

- レシート抽出側と同系統の **AI 自動カテゴリ生成・付与**
- 仮定パック重量などによる単価表示
- A の登録フローへの埋め込み
- **値札 OCR を本流の店頭フローにすること**（延期。優先度は買い物メモより下）

## 4. カテゴリ設計

### 4.1 A: AI / 学習カテゴリ（B は使わない）

- A の `main_category` / `sub_category` は支出分類・汎用検索用。
- B の比較対象集合には **持ち込まない**。

### 4.2 B: 手動フォルダのみ

- ユーザーがフォルダ（例: 「鶏むね」「牛乳 1L」「比較したい卵」）をマニュアルで作り、その中に厳密レコードを入れる。
- B のカテゴリは「比較したい集合の意図的な棚」。

```
A: レシート明細 ──(AI)──▶ main/sub_category  ──▶ 汎用検索・家計分類
B: 厳密レコード ──(手動)──▶ Folder            ──▶ 比較対象の明示的な集合
```

## 5. 連携モデル（一方向・任意）

```
[B 厳密定義・比較]  ──参照・検索（任意）──▶  [A レシート DB]
        │
        └── 保持しうるのは B 側の「紐付け先レシート明細 ID」など
```

- A は B を知らない。**B の完結に A は必須ではない**（別アプリ）。
- A 連携は自動化目的ではない。便利な下書き入力・事後の参照紐付けに使う。
- **厳密レコードは購入日・店・値段・数量が揃って初めて完成**する。A 待ちで空欄のまま保存しない。
- 登録の型:
  1. **レシート事後**: A を検索 → 見つかれば日付・店・値段を下書き。見つからなければ同項目を手動入力（必須）。数量・単位は常に手動。
  2. **A なしで分かる場合**: 日付・店・値段をそのまま手動入力。A を開かなくてよい。
  3. **店頭・観察**: 買い物メモの試算から任意保存（買っていなくても統計として可）。
  4. **事後紐付け**: 完成済みレコードへ参照用 ID を後付けしてもよい（需要は低く、独立タブは見直し可）。
- `recorded_at` の意味は **購入日（または店頭確認日）**。アプリ保存時刻は `created_at`。

## 6. 現行機能の扱い（A 側ステータス）

| 現状（A） | 変更方針 |
|-----------|----------|
| メモタブ（値段推移・価格比較） | A から削除済み。同等機能は **B に実装** |
| `is_comparable` / メモ用検索 / `memo_rows` | A から削除済み |
| 店頭照会（OCR） | **B でも本流にしない**。買い物メモ＋試算で代替 |
| AI カテゴリ自動設定 | A のみ。B には作らない |

## 7. B のデータ方針（確定データのみ）

- 未確定の重量・個数は厳密単価比較の対象外。仮定値は入れない。
- 規格が明確な商品でも、B では「フォルダに入れたもの」だけが比較対象。
- 試算で数量が取れないときは単価判定を出さない。
- ラベル写真 OCR は将来の補助候補にすぎず、必須フローではない。

## 8. 実装フェーズ（B）

優先度は変更しうる。

1. **ドキュメント・スキャフォールド** — 完了
2. **B テーブル + フォルダ CRUD** — 完了（Dev 適用済み）
3. **厳密レコード UI + 値段推移** — 完了
4. **A 任意下書き／参照** — 初版あり（事後紐付けタブは見直し可）
5. **買い物メモ**（`price_memo_items` による店頭リスト＋統計＋試算）— **完了**
6. **店舗カタログ**（`price_stores`・`StoreField`）— **完了**
7. **フォルダタブ**（品目名／店名・記録モーダル）— **完了**
8. 値札 OCR 店頭照会 — **延期**（非本流）

## 9. 非目標

1. レシート登録時の「比較対象にするか」選択（A 側）
2. A の記録フローへの重量・個数入力の常設
3. 仮定パック重量による単価表示
4. インストアコード / JAN だけで生鮮重量を汎用自動取得することへの依存
5. 単一 UI 内でのざっくり比較と厳密比較の同居
6. B への AI 自動カテゴリの持ち込み
7. **値札 OCR を店頭の必須・本流フローにすること**
8. A 待ちの未完成レコードを店頭判断の前提にすること

## 10. 用語

| 用語 | 意味 |
|------|------|
| A | レシート管理（`receipt-manager`） |
| B | 厳密定義・単価比較（本リポジトリ `price-memo`） |
| フォルダ | B における手動カテゴリ。比較したい商品集合の棚 |
| 買い物メモ | 店頭用ピン留めリスト（`price_memo_items`）＋統計ビュー＋行内試算＋任意保存 |
| 店舗カタログ | `price_stores` による店名の正規化。記録の `store_name` と整合 |
| 紐付け | B の厳密レコードと A のレシート明細を対応付けること（任意） |
| 厳密単価 | g / 個 / ml など単位あたりの価格。確定データのみ |
| 試算 | 保存前に総額と数量から単価を出し、過去統計と比較すること |
